# Methodology

> Документ уровня репозитория. Английская версия: [METHODOLOGY.md](METHODOLOGY.md).
> Полный контракт — [ARCHITECTURE.md](../ARCHITECTURE.md) §7–§8; этот файл —
> адаптация цикла разработки для читателя-контрибьютора.

## Зачем методология

Каждый проект репозитория прошёл один и тот же конвейер. Это не бюрократия:
конвейер гарантирует три вещи, ради которых репозиторий существует, — код
работает (тесты реально запускались), код объясним (нет «магии» для новичка)
и объём не расползается (scope зафиксирован заранее). Если ты вносишь вклад,
прохождение тех же шагов сохранит эти гарантии.

## Цикл из шести шагов

### 1. Lock scope

До первой строки кода фиксируется 2–3 предложениями: чему проект учит и что
явно вне рамок. Запись живёт в начале README проекта («What you learn» /
«Что изучаем»). Смысл: соблазн «добавить ещё одну фичу» проверяется против
записанного обещания, а не против настроения автора.

### 2. Код тремя этапами

- **minimal** — работает на минимальном наборе сущностей;
- **improved** — валидация, типизация, обработка краёв;
- **production-like** — тесты, линт, документация.

Этапы описаны в README каждого проекта. Это же — естественные контрольные
точки, если используешь проекты как задания.

### 3. Technical review — реальными прогонами

Правило G-18: «тесты зелёные» — это факт исполнения, а не заявление.
Полный гейт внутри папки проекта:

```bash
pytest -v          # все тесты зелёные
ruff check .       # линтер чист
black --check .    # формат без изменений
mypy src           # обычный mypy для 01–10; --strict для 11–20 (GRILL2-04)
```

Сводная строка вида `45 passed in 0.67s` записывается в
[PROGRESS_ru.md](PROGRESS_ru.md); полный вывод остаётся CI-логам.

### 4. Pedagogical review — отдельным проходом

Техническая зелень не закрывает вопрос «понятен ли код новичку». Отдельный
проход проверяет: каждая нетривиальная строка объяснена (комментарием или
README), нейминг читается в учебном контексте, бизнес-логика не спрятана в
`cli.py`. Необъяснённая магия приравнивается к багу.

### 5. Fix loop — максимум две итерации

Замечания из ревью исправляются не более чем за два прохода. Критерий выхода —
ноль открытых багов и ноль необъяснённых мест, а не «идеал». Правило G-04:
если что-то осталось после двух итераций, это переносится в
`known-issues.md` (создаётся по необходимости) с тегом `[project-NN]`, проект
закрывается со статусом `done-with-known-issues`.

### 6. Done

Тесты реально зелёные, документация парная (`README` ↔ `README_ru`,
`ELI5` ↔ `ELI5_ru`), статус отмечен в PROGRESS_ru.md.

## Правила, которые нельзя обойти

Полный список — ARCHITECTURE.md §9; критичные для контрибьютора:

- **Ровно 20 проектов (G-05).** Новые папки проектов как PR не принимаются.
- **Изоляция:** никаких импортов между `projects/*`; исключение — копипаста-
  снепшот проекта 20 из 04/11/16.
- **Без сети в тестах (G-12):** HTTP мокается, SQLite во временных каталогах.
- **Зависимости:** только в `requirements.txt` проекта, пиннинг `==`;
  `pyproject.toml:dependencies = []`.
- **Языки (G-10):** документы уровня репозитория — русский; документы
  проектов — двуязычные пары, меняются вместе.

Как применять при вкладе — см. [CONTRIBUTING.md](../CONTRIBUTING_ru.md).
