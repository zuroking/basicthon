# Contributing to basicthon

> English version: [CONTRIBUTING.md](CONTRIBUTING.md)

Спасибо за желание улучшить репозиторий. Этот документ объясняет, какие
изменения приветствуются, как устроен репозиторий и какие правила
зафиксированы контрактом.

## Устройство репозитория

Контракт дизайна — **[ARCHITECTURE.md](ARCHITECTURE.md)** (v3.1, стабильный)
— читай до предложения структурных изменений. Коротко:

- `projects/NN-slug/` — двадцать самодостаточных учебных проектов, каждый со
  своим `pyproject.toml`, `requirements.txt`, `src/<package>/`, `tests/`,
  двуязычными доками и (где нужно) `.env.example`.
- `docs/` — рабочие документы уровня репозитория: `PROGRESS_ru.md` (статус +
  сводные pytest), `LEARNING-PATH_ru.md`, `METHODOLOGY_ru.md`.
- Корень: витринные README, `SECURITY.md`, `CLAUDE.md`, `ELI5.md`, пиннутые
  dev-инструменты в `requirements-dev.txt`.

Стандарты кода — в ARCHITECTURE.md §5; пиннутый тулчейн — в
[`requirements-dev.txt`](requirements-dev.txt) (`ruff`, `black`, `mypy`,
`pytest`). Ворота качества на проект: `ruff check .`, `black --check .`,
`mypy` (обычный для 01–10, `--strict` для 11–20), `pytest -v`.

## Что принимаем

- **Багфиксы** существующих проектов (код или тесты).
- **Улучшения тестов** — лучшее покрытие публичных функций, более понятные
  сообщения о падениях.
- **Улучшения документации** — более ясные формулировки в любой паре
  README/ELI5; обе языковые версии меняются вместе.
- **Новые примеры в рамках существующего проекта** — например, дополнительная
  команда в CLI проекта 04, если она служит той же учебной цели.

## Что не принимаем

- **Новые проекты (21-я папка).** Репозиторий контрактом зафиксирован ровно
  на двадцати проектах (ARCHITECTURE.md §9, правило G-05). PR с новыми
  папками проектов будут закрываться — это решение об объёме, а не
  приглашение к торгу в ревью.
- **Межпроектные импорты и shared-модули.** Изоляция — ключевое ограничение
  дизайна: каждая папка должна работать автономно. Единственное
  санкционированное исключение (копипаста проекта 20 из 04/11/16 как
  снепшот) уже существует и расширений не требует.
- **Новые рантайм-зависимости без сильной мотивировки.** Рантайм-зависимости
  идут только в `requirements.txt` затронутого проекта, точный пиннинг `==`;
  `pyproject.toml:dependencies = []` остаётся пустым. Стиль дома — stdlib first.
- **Сетезависимые тесты.** Все тесты обязаны проходить офлайн (правило G-12):
  HTTP мокается, Telegram-апдейты — dict-фикстуры, SQLite во временных
  каталогах.
- **Ослабление строгости типов.** Проекты 01–10 используют обычный `mypy`;
  11–20 — `mypy --strict`. Не занижай ни одну сторону.

## Как предложить изменение

1. Сначала открой issue для всего, что больше правки опечатки — опиши
   проблему, а не только решение.
2. Работай внутри одной затронутой папки проекта; держи изменения в рамках.
3. Убедись, что полный гейт проходит локально:

   ```bash
   cd projects/NN-slug
   pip install -e .
   pip install -r requirements.txt
   pytest -v          # реально запусти
   ruff check .
   black --check .
   mypy src           # --strict для проектов 11-20
   ```

4. Если изменение влияет на задокументированное поведение — обнови `README.md`
   проекта **и** `README_ru.md` в одном PR (двуязычные пары зеркалят друг
   друга), плюс `docs/PROGRESS_ru.md`, если меняется число тестов.
5. Держи педагогическую планку: код этих проектов рассчитан на чтение
   новичками. Предпочитай очевидное хитрому, объясняй *почему* в комментариях,
   где шаг неочевиден, держи бизнес-логику вне `cli.py`.

## Security-чувствительные области

Проекты 12 и 17 (и auth/storage паттерны в 16–20) — сознательно упрощённые
учебные реализации — см. [SECURITY.md](SECURITY.md). PR, добавляющие туда
продакшн-харденинг, приветствуются только при сохранении читаемости для
новичка; PR, убирающие предупреждения «educational only», — нет.
