# АРХИТЕКТУРА — 12 Менеджер секретов

> Требуется по критерию ARCHITECTURE.md §6 (≥2 решения из {выбор крипто-примитива, схема хранения, обработка ключа, схема БД, retry/backoff}) — у проекта все три первых.

## 1. Решения

### 1.1 Крипто-примитив — Fernet (cryptography)

**Выбран:** `cryptography.fernet.Fernet` — AES-128 в CBC + PKCS7 + HMAC-SHA256 для аутентификации, с меткой времени и IV на токен. Высокоуровневый, устойчивый к ошибкам использования. Ключ — 32 случайных байта в urlsafe-base64 (44 символа).

**Почему не альтернативы:**

- **Только `hashlib`/std `secrets` + `base64`:** в stdlib нет аутентифицированного шифрования. `secrets` хорош для генерации паролей (проект №03), но для хранения секретов нужны конфиденциальность + целостность. Собирать AES из `hashlib` — небезопасно.
- **Ручной AES-GCM с `Crypto`/`pyaes`:** низкоуровневый, требует корректной работы с nonce, проверки тега и деривации ключа. Легко ошибиться (повтор nonce, пропущенная аутентификация). Fernet упаковывает это в один вызов `Fernet(key).encrypt(plaintext)`.
- **Низкоуровневый `AESGCM` / `ChaCha20Poly1305` из `cryptography`:** тоже безопасны, но требуют хранить nonce/тег рядом с шифртекстом. Fernet хранит всё внутри токена, упрощая JSON до `name -> token`.
- **Внешний KMS / `keyring`:** вне учебной цели, требует интеграции с ОС и сети.

**Зависимость:** `cryptography==42.0.8` с пиннингом `==` в `requirements.txt` (GRILL2-12). `pyproject.toml:dependencies = []`; рантайм только через `requirements.txt` по GRILL2-02. Stdlib сознательно недостаточен — без сторонней библиотеки нет подходящего примитива.

### 1.2 Схема хранения — JSON-файл с шифрованными значениями

**Выбран:** один JSON-файл (`secrets.json` по умолчанию, настраивается `--store` или `$SECRET_STORE_PATH`). Структура: `dict[str, str]`, ключи — имена секретов (после `strip`, непустые), значения — токены Fernet (urlsafe base64 `gAAAA...`). Запись через `json.dumps(indent=2, sort_keys=True)`, директории через `Path.parent.mkdir(parents=True)`.

**Почему JSON:**

- **Наглядность для новичка:** читаемый, только `json` + `pathlib`, без БД (в отличие от проекта №11). Легко убедиться, что открытого текста на диске нет.
- **Изоляция:** папку можно копировать, тесты на `tmp_path` с реальными файлами, без сервера.
- **Компромисс атомарности:** для обучения простота > надёжность. Делаем `write_text` целиком; нет WAL, блокировок, `fsync`. Достаточно для однопроцессного игрушечного использования.

**Отклонённые альтернативы:**

- **SQLite (как в №11):** избыточен для `name -> blob`. Колонки всё равно хранили бы токены; выгоды `LIKE` нет. JSON легче.
- **Dotenv / plain env:** хранит открытый текст, нет программного `list`/`delete`.
- **Шифрованный SQLite / SQLCipher:** тяжелее, доп. зависимости, скрывает урок "токены в JSON".
- **Файл на секрет:** много файлов, сложнее атомарный `list`.

**Обработка порчи:** `_load_store` возвращает `{}` если файла нет или он пуст. Бросает `ValueError("corrupted store: ...")` при невалидном JSON, верхнем уровне не-объекте или не-`str` значениях — явно сигнализирует о вмешательстве.

### 1.3 Обработка ключа — переменная окружения с фолбэком CLI

**Выбран:** мастер-ключ вне кода. Приоритет в CLI: `--key` > `$SECRET_MANAGER_KEY` > ошибка с подсказкой к `.env.example` / `generate-key`. Библиотека даёт `generate_key() -> str` (`Fernet.generate_key().decode()`) и `get_key_from_env(var_name="SECRET_MANAGER_KEY") -> str` (стрип, валидация `var_name`, `ValueError` если пусто). Функции менеджера принимают `key: str | bytes` и валидируют через `_get_fernet` (`Fernet(key_bytes)` → `ValueError("invalid Fernet key")`).

**Почему env:**

- Учит 12-фактору: секреты не в репозитории, не в JSON, только токены на диске.
- `.env.example` документирует контракт без реального ключа, по GRILL2-06. Содержит `SECRET_MANAGER_KEY=your-44-char...` и `SECRET_STORE_PATH`.
- CLI-фолбэк удобен: `secret-manager set foo bar --key $KEY` работает без env.

**Отклонено:**

- **Ключ внутри JSON:** обессмысливает шифрование.
- **Хардкод / `input()`:** не скриптуемо, провоцирует коммитить ключи.
- **Деривация из пароля (PBKDF2/Argon2):** добавляет UX пароля и параметры KDF; вне scope. Можно как расширение, но нужна соль и подбор итераций.
- **Только `bytes`-ключ:** `str` удобнее для env; принимаем `str | bytes` и нормализуем через `.encode("utf-8")`.

## 2. Границы модулей

- `manager.py` — чистая логика: `pathlib` + `json` + `Fernet` + `os` (только для `get_key_from_env`). Нет `argparse`/`print`/`sys.exit`. Публичные функции валидированы и типизированы; приватные `_get_fernet`, `_load_store`, `_save_store`, `_validate_name` с `_` не покрываются критерием G-13.
- `cli.py` — тонкая обёртка I/O, исключена из покрытия: `argparse` (`generate-key/set/get/delete/list`), хелперы `_resolve_key`/`_resolve_store`, коды выхода, сообщения в `stderr`. Импортирует `manager`, не дублирует криптологию.
- `__init__.py` — реэкспорт `generate_key`, `get_key_from_env`, `set_secret`, `get_secret`, `delete_secret`, `list_secrets`.
- `__main__.py` — `python -m secret_manager`.

## 3. Почему не для продакшена (§9)

Сейф явно учебный (баннер в README). Нельзя хранить реальные секреты, потому что:

1. **Ключ в env всё равно утекает:** виден в списке процессов, дампах, логах; нет блокировки памяти/зануления.
2. **Нет ротации:** при смене ключа токены не перешифровываются; старые копии доступны только старым ключом; нет envelope encryption.
3. **Права файла не ужесточены:** JSON создаётся с дефолтной umask, без `0600`, без keychain/HSM.
4. **Нет атомарности/конкурентности:** параллельные `set_secret` могут затереть; нет блокировок/`fsync`/бэкапа.
5. **Один мастер-ключ, один файл:** нет скоупа, аудита, TTL, контроля доступа.
6. **Нет метаданных:** нет времени создания/версии/KDF-контекста; timestamp Fernet не используется для expiry.
7. **Нет надёжного удаления:** перезапись JSON не стирает старый открытый текст с диска/памяти.

Продакшен `secure-secrets-vault` (портфолио №8, отдельный репозиторий) использовал бы keychain/HSM, иерархию ключей, файлы `0600` с `fsync`+блокировкой или SQLite WAL, ротацию, аудит и защиту памяти — всё сознательно опущено здесь ради изоляции и читаемости.

## 4. Модель ошибок

- `ValueError` для пользовательских ошибок: пустое имя, не-`str` значение, невалидный ключ, отсутствие env, `secret not found` при `delete`, порча JSON, `InvalidToken` при `get` (неверный ключ/подмена).
- `get_secret` возвращает `None` при "не найдено" (нет файла/имени) — как `sqlite_notes.get_note`, удобно ветвиться без исключений.
- `list_secrets` возвращает `[]` для отсутствующего/пустого стора.
- `OSError` чтения/записи оборачивается в `ValueError` для унификации CLI.
