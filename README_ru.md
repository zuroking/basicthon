Двадцать изолированных, самодостаточных Python-проектов для начинающих,
выстроенных по возрастающей кривой сложности — от калькулятора на четырёх
функциях до приложения, объединяющего CLI, SQLite и REST API в одной папке.
Каждый проект учит конкретному набору навыков, поставляется с собственным
`README`, «объяснением на пальцах» (ELI5) и набором тестов, которые реально
проходят (655 тестов по репозиторию, все зелёные на момент написания).

> **Что это такое (и чем не является).** Это не курс с видео и квизами и не
> коллекция сниппетов для копипасты. Это *лестница*: вы читаете код проекта N,
> понимаете каждую строку, а затем используете это понимание, чтобы читать
> проект N+1. Проекты усложняются намеренно. Проект 12 (менеджер секретов) и
> паттерны авторизации/хранения в 16–20 — **учебные реализации, явно не для
> продакшена** — см. [SECURITY_ru.md](SECURITY_ru.md), прежде чем использовать
> что-то здесь по-настоящему.

## Зачем существует basicthon

Большинство материалов «научи меня Python» проваливаются одним из двух
способов:

1. **Игрушечные примеры, которые никогда не соединяются.** Вы пишете функцию,
   переворачивающую строку, и... что дальше? Настоящие программы — это файлы +
   состояние + интерфейсы. Поздние проекты basicthon комбинируют ровно это:
   CLI, говорящий с базой данных через API-слой.
2. **Фреймворки раньше фундамента.** Туториалы сразу прыгают к Django или
   pandas. Когда что-то ломается — а это произойдёт — у новичка нет ментальной
   модели того, что находится под капотом.

basicthon идёт противоположным путём: **сначала stdlib, фреймворки в конце**.
Первые десять проектов работают на чистом Python. Базы данных появляются
только после того, как вы почувствовали боль управления списками в памяти
(проект 04). FastAPI появляется только после того, как вы собрали CRUD-ядро
как обычные функции (проект 16 сначала показывает функции, потом оборачивает
их). К проекту 20 вы можете посмотреть на любое веб-приложение и узнать слои,
потому что построили их все своими руками.

Название намеренное: *thon* из *basics*. Двадцать проектов, каждый достаточно
маленький, чтобы закончить за вечер-два, каждый на шаг сложнее предыдущего.

## Для кого это

- **Новички, знающие синтаксис Python** (переменные, циклы, функции, классы),
  но ни разу не закончившие настоящую работающую программу.
- **Самоучки с пробелами**: вы можете писать скрипты, но никогда не писали
  тесты, не трогали SQLite напрямую, не видели, зачем у JWT есть claim `exp`.
- **Студенты перед стажировками**: проекты 11–20 читаются как вопросы с
  собеседований («сделай CRUD», «добавь auth», «объедини CLI + БД + API»).
- **Преподаватели и менторы**, которым нужен готовый каркас курса с порядком
  чтения по проектам и честными пометками о безопасности.

Если вы вообще не открывали Python, начните в другом месте (любой интерактивный
туториал) и возвращайтесь, когда знаете, что такое `for` и `dict`.
[ELI5_ru.md](ELI5_ru.md) объясняет весь репозиторий без предположения, что вы
программируете.

## Чем это отличается от других списков «20 проектов для новичков»

| Типичный список | basicthon |
|---|---|
| Абзац описания; без кода | Полный рабочий код каждого проекта |
| Без тестов | Каждая публичная функция протестирована; сводка в `docs/PROGRESS_ru.md` |
| Проекты никак не связаны | Намеренная кривая сложности: 04→11→16 возвращаются объединёнными в 20 |
| Копипаста приветствуется | Каждый проект объясняет, *почему* он написан именно так (заметка ZuroKing) |
| Молчит о безопасности | Явные предупреждения там, где учебный код нельзя использовать по-настоящему ([SECURITY_ru.md](SECURITY_ru.md)) |
| Единый монолит репозитория | Строгая изоляция: каждая папка работает автономно |

Правило изоляции стоит подчеркнуть, потому что оно формирует всё: **можно
удалить любые девятнадцать папок, оставшаяся продолжит работать.** Никаких
общих модулей, никаких импортов между проектами, никакого корневого пакета.
Это ограничение стоит дублирования (проект 20 копирует код из 04/11/16 по
замыслу) и покупает независимость: скачал одну папку, `pip install -e .`,
готово.

Чистая стандартная библиотека. Ввод/вывод, типы данных, обработка ошибок,
персистентность в файлах. Классы не требуются до 06, хотя появляются естественно.

| 02 | [Угадай число + КНБ](projects/02-guess-number-rps/) | Случайность, игровые циклы, валидация ввода, отделение правил от интерфейса |

Они существуют, чтобы безопасно teach concepts; что именно упрощено и почему —

## Архитектура репозитория

Полный архитектурный контракт живёт в [`ARCHITECTURE.md`](ARCHITECTURE.md)
(v3.1, стабильный, source of truth). Здесь — короткая версия и рассуждения
за ней.

### Изоляция проектов

Каждая папка в `projects/` — завершённое автономное приложение:

```text
projects/NN-project-slug/
├── README.md / README_ru.md      # использование, этапы, заметка автора
├── ELI5.md / ELI5_ru.md          # объяснение простым языком
├── ARCHITECTURE.md(_ru)          # только где решения того требуют (§6)
├── pyproject.toml                # конфигурация сборки, ruff/black/mypy/pytest
├── requirements.txt              # единственный источник рантайм-зависимостей
├── .env.example                  # везде, где используется os.environ
├── src/<package>/                # импортируемый пакет
└── tests/                        # набор pytest, без сети
```

Почему изоляция вместо монорепо с общими утилитами?

- **Учащиеся скачивают одну папку.** Студенту, работающему над погодным CLI,
  не нужны зависимости Telegram-бота, его история и его тесты.
- **Честность зависимостей.** Каждый проект объявляет ровно то, что ему нужно.
  Нет невидимой корневой среды, маскирующей пропущенные объявления.
- **Свобода копирования.** Преподаватель может взять один проект в свой курс,
  не таща половину репозитория.

Цена — осознанное дублирование: проект 20 намеренно *копирует* (никогда не
импортирует) код из проектов 04, 11 и 16, чтобы остаться автономным. Это
зафиксировано в его README как снепшот-решение.

### Инструменты на уровне проекта

Каждый проект несёт собственный `pyproject.toml` с секциями `[tool.ruff]`,
`[tool.black]`, `[tool.mypy]`, `[tool.pytest.ini_options]`. Корневого
pyproject нет сознательно:

- CI гоняет каждый проект против *его собственной* конфигурации, поэтому
  проект не может молча полагаться на обще-репозиториевскую снисходительность.
- Проекты остаются переносимыми: конфиг едет вместе с папкой.
- Dev-инструменты (`ruff`, `black`, `mypy`, `pytest`) лежат один раз в
  корневом [`requirements-dev.txt`](requirements-dev.txt); рантайм-зависимости —
  в `requirements.txt` каждого проекта с точным пиннингом `==`. Обычный pip,
  без poetry/pipenv — новичок должен сначала освоить инструменты, работающие
  везде, прежде чем учить opinionated обёртки над ними.

Проверка типов разделена по уровням: проекты 01–10 проходят обычный `mypy`;
проекты 11–20 обязаны проходить `mypy --strict`. Строгий режим приходит
вместе с настоящим персистенсом и HTTP-кодом, где ошибки типов перестают быть
теоретическими.

### CI-матрица

План CI (специфицирован в ARCHITECTURE.md §3, правило GRILL2-07) использует
две стадии: job `discover` динамически перечисляет `projects/*/` и передаёт
список в `strategy.matrix`; каждый job матрицы пинает Python 3.11 через
`actions/setup-python`, ставит dev-инструменты с pip-кэшем по хэшу
`requirements-dev.txt`, ставит requirements проекта и запускает `ruff check`,
`black --check`, `mypy` (соответствующего уровня) и `pytest -v` только внутри
папки этого проекта. Единого прогона в корне нет: сломанный проект падает один.

> Примечание: файл воркфлоу `.github/workflows/ci.yml` — **запланирован, но
> ещё не реализован**; спецификация выше зафиксирована в ARCHITECTURE.md, а те
> же ворота сейчас гоняются локально по каждому проекту (`ruff` / `black` /
> `mypy` / `pytest`).

## Выбор технологий по уровням

Коротко, без философии: каждый выбор — простейшая вещь, честно обучающая
концепции.

- **01–10: только stdlib.** Смысл этих уровней — сам Python: функции, классы,
  файлы, хеширование, время. Любая сторонняя зависимость была бы шумом. Даже
  проект 03 использует `secrets`, а не `random`, потому что это различие и
  *есть* урок.
- **11–12: SQLite и Fernet.** Проект 11 использует сырой `sqlite3`, чтобы
  новички увидели SQL-строки, параметры и маппинг строк — ORM-магия позже,
  если вообще. Проект 12 использует Fernet из `cryptography`, потому что
  придумывать своё шифрование — классическая катастрофа новичка; использовать
  аудированные примитивы — вот урок.
- **13–15: httpx, retry-логика, цепи Маркова.** Первый контакт с сетевым кодом
  всегда мокается в тестах; конвертер кэширует курсы офлайн; погодный CLI
  считает сбой нормой (retry/backoff). Проект 15 остаётся на stdlib — цепям
  Маркова нужны словари, а не библиотеки.
- **16–17: FastAPI + Pydantic (+ PyJWT, bcrypt).** Декораторная модель FastAPI
  чисто ложится на «тонкую обёртку над обычными функциями» — именно так
  устроен 16: CRUD-ядро существует до любого роута. PyJWT и bcrypt —
  минимальные аудированные выборы для урока авторизации.
- **18: Bot API через сырой httpx.** SDK для Telegram спрятал бы
  request/response цикл, которому посвящён этот проект. Long polling — около
  40 строк на httpx.
- **19: локальный HTTP API Ollama.** Local-first AI оставляет данные на машине
  и убирает API-ключи с пути новичка полностью. Тот же навык, что в 18,
  другой эндпоинт.
- **20: всё вышеперечисленное вместе.** fastapi + uvicorn + sqlite3,
  склеенные одним модулем `storage.py`, который вызывает и CLI, и API.

## Как пользоваться репозиторием

Три рекомендованных пути, в зависимости от цели:

1. **Последовательный (рекомендован новичкам):** делайте 01 → 20 по порядку.
   Читайте README проекта, запускайте его тесты (`pytest -v`), ломайте вещи
   специально, чините. Ожидайте примерно 2–4 вечера на проект Foundations и
   больше для Systems & Integration.
2. **Закрытие пробелов (для самоучек):** прыгайте к тому, чего не хватает.
   Таблица выше говорит, что предполагает каждый проект. Если 17 кажется
   сложным, проведите час с 16 — кривая связана намеренно.
3. **Как справочник (менторам):** берите проекты как задания. Каждый README
   фиксирует lock scope (что изучается) и три этапа сборки (minimal →
   improved → production-like), которые естественно ложатся на оцениваемые
   контрольные точки.

Подробное руководство — в `docs/LEARNING-PATH_ru.md`; заметки по методологии
проекта — в `docs/METHODOLOGY_ru.md`.

Цикл для каждого проекта одинаков:

```bash
cd projects/NN-project-slug
pip install -e .
pip install -r requirements.txt
pytest -v        # убедитесь, что зелёное, прежде чем менять что-либо
python -m <package> --help
```

Затем прочитайте `src/<package>` сверху вниз — ни один модуль не длиннее
нескольких сотен строк, и каждое неочевидное решение либо закомментировано,
либо объяснено в README.

## Методология разработки

Каждый проект прошёл один и тот же конвейер (полный текст: `METHODOLOGY_ru.md`,
контракт: ARCHITECTURE.md §7):

1. **Lock scope.** Два-три предложения в README: чему учимся, что вне рамок.
   Предотвращает расползание фич.
2. **Написание кода тремя этапами.** Minimal (работает) → improved
   (валидация, типы) → production-like (тесты, линт, документация).
3. **Technical review реальными прогонами.** `pytest -v`, `ruff check`,
   `black --check`, `mypy` — исполненные, а не заявленные. Сводки вывода
   зафиксированы по каждому проекту в [`docs/PROGRESS_ru.md`](docs/PROGRESS_ru.md).
4. **Pedagogical review.** Отдельный проход: объяснён ли каждый трюк? Понял бы
   новичок нейминг? Необъяснённая «магия» считается багом.
5. **Fix loop.** Максимум две итерации после review; оставшиеся известные
   недочёты идут в `docs/known-issues.md`, а не блокируют релиз.
6. **Done.** Тесты реально зелёные, документация сгенерирована, прогресс отмечен.

Сама архитектура репозитория прошла три раунда состязательного опроса
(«grill-me») до начала реализации — changelog в ARCHITECTURE.md показывает
каждое решение и его происхождение.

## Тестирование

Все 655 тестов в 20 проектах проходят, и ни одному не нужны сеть, API-ключи,
запущенный Ollama или Telegram-токен:

```bash
# один проект
cd projects/16-fastapi-crud && pytest -v

# всё (из корня репозитория, пример PowerShell)
Get-ChildItem projects | ForEach-Object {
  Push-Location $_.FullName; python -m pytest -q; Pop-Location
}
```

Политика мокирования: HTTP перехватывается (`httpx.post` заменяется
in-process), Telegram-апдейты — dict-фикстуры, ответы Ollama — консервированный
JSON, SQLite — временные каталоги. Если тесту нужен интернет, ему не место в
этом репозитории.

Сводки по проектам (число тестов и тайминги) — в
[`docs/PROGRESS_ru.md`](docs/PROGRESS_ru.md).

## Конвенции документации

Языковое разделение сознательное (ARCHITECTURE.md §1):

- Документы репозитория идут двуязычными парами (`LEARNING-PATH.md` ↔
  `LEARNING-PATH_ru.md`, `METHODOLOGY.md` ↔ `METHODOLOGY_ru.md`) — написаны на русском, потому что это рабочие
  документы автора.
- Документы отдельных проектов — двуязычные пары (`README.md` ↔
  `README_ru.md`), потому что английский README делает проект дружелюбным к
  портфолио.

Каждый проектный README следует одному шаблону: lock scope → установка (всегда
те же две команды) → использование → детали → три этапа → API → тестирование →
заметка ZuroKing → заявление об изоляции. У каждого проекта есть и вариант
ELI5, объясняющий его без жаргона.

## Замечание о безопасности

Коротко и заметно, потому что это важно: несколько проектов реализуют
функциональность, смежную с безопасностью, как **учебные упрощения**. В
частности, проект 12 хранит секреты с настоящим шифрованием Fernet, но
опускает всё, что нужно настоящему сейву (ротацию ключей, жёсткие права,
защиту памяти), а проект 17 демонстрирует JWT-авторизацию с in-memory
хранилищем пользователей и dev-ключом по умолчанию. Ни один из двадцати
проектов не должен охранять настоящие креденшелы. Полный список упрощений,
политика `.env.example` (только плейсхолдеры — никогда не коммитить реальные
секреты где-либо в этом репозитории) и путь сообщения об уязвимости — в
[SECURITY_ru.md](SECURITY_ru.md).

## Предпосылки и результаты по каждому проекту

Каждая запись: что знать *до* старта и что вы сможете делать *после*.
Используйте, чтобы прыгать между уровнями, не ломая кривую сложности.

**01 — CLI-калькулятор.**
До: переменные, функции, `if`. После: чтение грамматики из AST,
whitelisting вместо blacklisting (секьюрити-инстинкт), построение
read-eval-print цикла.

**02 — Угадай число + камень-ножницы-бумага.**
До: циклы. После: конечные автоматы игровых состояний, `random` vs
seeded-детерминизм в тестах, разделение «правил игры» и «общения с игроком».

**03 — Генератор паролей.**
До: строковые методы. После: почему `random` предсказуем, а `secrets` — нет;
политики классов символов; дизайн CLI-флагов, которые реально запоминаются.

**04 — To-do CLI.**
До: списки и словари. После: dataclasses как типизированные записи,
JSON round-trips, почему id никогда не переиспользуются, CRUD-модель, которую
переиспользуют все поздние проекты.

**05 — Анализатор оценок.**
До: словари. После: реалии CSV (заголовки, кодировки, пустые строки),
агрегация (mean/median/распределение), сортировка по ключам.

**06 — Контакты (ООП).**
До: функции. После: классы как чертежи, контракты `__eq__`/`__hash__`,
когда класс лучше dict — а когда нет.

**07 — Организатор файлов.**
До: основы `pathlib`. После: правила-маппинги как данные, dry-run перед любой
разрушающей операцией, идемпотентные скрипты.

**08 — Поиск дубликатов.**
До: хеширование концептуально. После: фильтр «сначала размер» для скорости,
хеши содержимого для корректности, обход больших деревьев без зависания.

**09 — Таймер/логгер.**
До: ничего особенного. После: монотонные vs настенные часы, структурные логи
сессий, форматирование длительностей, читаемых людьми.

**10 — Мини тест-фреймворк.**
До: немного пользовались pytest. После: discovery, переписывание ассертов в
игрушечном масштабе, генерация отчётов — вы перестаёте бояться pytest, потому
что построили его младшего брата.

**11 — SQLite заметки.**
До: файловая персистентность (04). После: схемы, `AUTOINCREMENT`,
параметризованные запросы (и почему SQL через форматирование строк — так
взламывают новичков), маппинг строк в объекты. mypy становится strict отсюда.

**12 — Менеджер секретов (учебный).**
До: привычки хранения из 11. После: аутентифицированное шифрование vs простое
кодирование, токены Fernet, доставка ключей через env — плюс честный список
того, что добавляет настоящий сейф.

**13 — Конвертер валют.**
До: типизация уровня 11. После: клиенты `httpx`, мокирование сетевых ответов,
чтобы тесты оставались офлайн, кэширование курсов для работы без сети.

**14 — Погодный CLI.**
До: 13. После: таймауты везде, retry с backoff, сбой API как обычная ветка
кода, а не исключение.

**15 — Markov-генератор.**
До: словари словарей. После: таблицы частот, сэмплирование, тестирование
случайного вывода через seed.

**16 — FastAPI CRUD.**
До: зрелость 11–15. После: REST-глаголы и статус-коды как словарь,
Pydantic-модели как пограничная охрана, TestClient, правило 204-без-тела.

**17 — FastAPI JWT (учебный).**
До: 16. После: bcrypt-хеширование паролей, структура JWT (header.payload.
signature), expiry claims, Bearer-заголовки — и ровно то, какие продакшн-
шаги были пропущены.

**18 — Telegram-бот.**
До: типизация 16, любой опыт HTTP-клиентов. После: long polling, offset-
курсоры, обработка ошибок внешнего сервиса, гигиена токенов.

**19 — Ollama-чатбот.**
До: HTTP-привычки 18. После: массивы chat-сообщений, обрезка контекста,
локальные LLM-серверы, мокирование медленных зависимостей.

**20 — Финальная интеграция.**
До: паттерны 04 + 11 + 16 (здесь они повторно преподаются копиями). После:
слоистая архитектура — один storage-модуль обслуживает и CLI, и API — это
форма большинства настоящих программ.

## Как правильно читать проект: экскурсия

Вот как работать с любым проектом, на примере **16-fastapi-crud**. Рецепт
работает для всех двадцати.

1. **Прочитайте lock scope** (первый абзац README). Теперь вы знаете границы:
   in-memory хранилище, пять роутов, без базы данных. Всё за пределами — вне
   рамок по замыслу; не добавляйте этого во время обучения.
2. **Запустите тесты до чтения кода:**

   ```bash
   cd projects/16-fastapi-crud
   pip install -e .
   pip install -r requirements.txt
   pytest -v
   ```

   Сорок пять тестов проходят меньше чем за секунду, офлайн. Вы только что
   доказали, что код работает — теперь выясните, почему.
3. **Сначала прочитайте `models.py`** (~44 строки). Три Pydantic-класса
   определяют, как выглядит задача и что считается валидным вводом. Это
   словарь всего проекта.
4. **Читайте `app.py` сверху вниз.** Первая половина — обычные функции над
   dict — create/get/list/update/delete. Заметьте: здесь ноль FastAPI. Только
   во второй половине появляются тонкие роуты-обёртки, каждый по три строки:
   провалидировать, вызвать функцию, превратить `None` в 404.
5. **Сломайте что-то нарочно.** Поменяйте `min_length=1` на `min_length=5`
   в `models.py`, перезапустите pytest, посмотрите, какие ровно два теста
   упали, прочитайте их сообщения. Вы только что увидели, *зачем* нужны
   тесты.
6. **Прочитайте заметку ZuroKing.** Она сжимает проект в один инсайт: слой
   хранения тривиально прост, и именно эта простота делает обёртку API
   читаемой.
7. **И только теперь расширяйте.** Добавьте эндпоинт поиска. Сначала напишите
   его тест. Вы только что самостоятельно выполнили шаг 2 методологии.

Общее время: один сосредоточенный вечер. Умножьте на двадцать проектов — и у
 вас портфолио, а не просто домашка.

## Решение проблем

Частые проблемы первого запуска и их исправления:

- **`python: can't open file 'src/cli_calculator/__main__.py'`** — команда
  запущена из корня репозитория. Каждый проект запускается *из своей папки*
  (сначала `cd projects/NN-slug`).
- **`ModuleNotFoundError: No module named 'cli_calculator'`** — пропущен
  `pip install -e .`. Он регистрирует пакет против текущего интерпретатора.
- **Тесты падают с ошибками соединения** — не должны; если упали, переменные
  прокси могут мешать HTTP-мокам. Сбросьте `HTTP_PROXY`/`HTTPS_PROXY` на время
  прогона тестов.
- **`mypy` ведёт себя иначе, чем описано** — проверьте уровень: проекты 01–10
  используют обычный `mypy`, 11–20 — `mypy --strict`.
- **Кириллица выглядит сломанной в выводе инструментов** — это обычно
  кодировка консоли PowerShell 5.1, а не файлов. Сами файлы в UTF-8.
- **Зависимость не ставится на Python 3.14** — пины нацелены на 3.11+;
  для гладкого результата используйте Python 3.11–3.13, как CI.

## FAQ

**Почему именно Python 3.11?** CI пинает её, все конфиги объявляют
`requires-python = ">=3.11"`, синтаксис 3.12+ нигде не использован — поэтому
3.11–3.13 работают локально. Одна цифра, никакого per-project дрейфа.

**Почему конфиг ruff/black/mypy/pytest повторяется в каждом проекте?** Чтобы
каждая папка была действительно автономной: скопируйте куда угодно — её
ворота качества едут вместе с ней. Общий конфиг создал бы невидимую связность.

**Почему не poetry / uv / pipenv?** С ними всё нормально — но каждый добавляет
концепты (lockfiles, мнение о virtualenv) раньше, чем у учащегося появится
причина о них заботиться. Обычный `pip install -e .` + `requirements.txt`
работает везде, включая CI-матрицы.

**Можно ли использовать эти проекты в портфолио?** Да — это часть замысла
(английские README, чистые коммиты). Две честные оговорки: держите метки
«educational only» видимыми на проектах 12 и 17 (ревьюеры ценят честность
больше бравады) и будьте готовы объяснить каждую строку — на собеседовании
спросят.

**Можно ли добавить новый проект?** Не как 21-ю папку — количество зафиксировано
на 20 контрактом (ARCHITECTURE.md §9). Улучшения, переводы и багфиксы
существующих проектов приветствуются через CONTRIBUTING.md.

**Почему доки репозитория на русском, а проектов — двуязычные?** Сознательное
разделение (ARCHITECTURE.md §1): внутренние рабочие документы служат автору;
проектные README служат мировой аудитории. Оба решения записаны, чтобы никто
не гадал.

**Сколько времени займёт вся лестница?** Грубая математика: Foundations по
2–4 вечера, Structures & Patterns похоже, Data & Algorithms и Systems &
Integration дольше — итого примерно 60–100 сосредоточенных вечеров от начала
до конца. Быстрее, если уже программируете на другом языке; медленнее — тоже
нормально.

## Как строился сам репозиторий

Мета, но полезно любому, кто поддерживает похожий учебный план: basicthon
писался не экспромтом. До появления какого-либо кода проектов архитектура
репозитория прошла три раунда состязательного ревью (внутренне называется
«grill-me»), где агент оспаривал каждое проектное решение, пока у каждого не
появилась записанная мотивировка — решения G-01…G-19 и GRILL2-01…GRILL2-12
можно проследить в ARCHITECTURE.md §11.

Затем каждый из двадцати проектов прошёл один и тот же шестишаговый конвейер
(lock scope → трёхэтапная реализация → technical review с реальными прогонами
инструментов → pedagogical review → ограниченный fix loop → done), с правилом
эскалации: любое противоречие с архитектурным контрактом останавливает линию,
если затрагивает текущий проект, или откладывается в `docs/known-issues.md`,
если далёкий. Ничто в этом репозитории не exempt от собственных правил —
включая документацию, которую вы сейчас читаете: её двуязычные пары тоже
обязаны зеркалить друг друга.

Практическое следствие: если хотите узнать, *почему* что-то выглядит именно
так, ответ всегда находим — либо в README проекта, либо в ARCHITECTURE.md
проекта (для 12/17/20), либо в changelog контракта репозитория. Никакого
фольклора, никаких племенных знаний.
