# CLAUDE.md

Руководство для AI-ассистентов (Claude или любых других), работающих в этом
репозитории.

## Проект

`basicthon` — открытый учебный репозиторий из ровно **20 изолированных
Python-проектов** для начинающих, упорядоченных по возрастанию сложности
(Foundations 01–05 → Structures & Patterns 06–10 → Data & Algorithms 11–15 →
Systems & Integration 16–20). Python **3.11** (`.python-version` пинает
`3.11`; все `pyproject.toml` требуют `>=3.11`).

Контракт дизайна — **ARCHITECTURE.md** в корне репозитория (русская версия:
ARCHITECTURE_ru.md) — статус СТАБИЛЬНО v3.1, source of truth. Читай его до любых структурных изменений.
§9 перечисляет явные non-goals; §11 changelog объясняет, почему решения
именно такие.

## Непреложные правила

Нарушение любого из них — баг, даже если тесты зелёные:

- **Ровно 20 проектов (G-05).** Никогда не предлагай и не создавай 21-й
  проект. Добавление требует явного письменного решения автора вне любого
  review-цикла.
- **Изоляция проектов.** Никаких shared/-модулей, никаких импортов между
  папками `projects/*`, никакого корневого `pyproject.toml`. Единственное
  санкционированное исключение: проект 20 может *копипастить* (никогда не
  импортировать) код из проектов 04, 11 и 16 — как снепшот.
- **Только реальные прогоны тестов (G-18).** Никогда не заявляй «тесты
  проходят», не исполнив их. В `docs/PROGRESS_ru.md` записывай только
  summary-строки (`N passed in Xs`); полный вывод остаётся в CI-логах.
- **Без сети в тестах (G-12).** HTTP мокается in-process, Telegram-апдейты —
  dict-фикстуры, ответы Ollama — консервированный JSON, SQLite — временные
  каталоги. Тест, требующий интернета или реальных ключей, здесь существовать
  не должен.
- **Политика секретов.** `.env.example` содержит только плейсхолдеры и подсказки
  по генерации. Если найдёшь где-либо закоммиченный реальный токен/ключ/пароль —
  стоп и немедленно эскалируй автору.
- **Разделение строгости mypy (GRILL2-04).** Проекты 01–10: обычный `mypy`.
  Проекты 11–20: `mypy --strict`. Не ослабляй ни одну сторону.
- **Зависимости.** Рантайм-зависимости идут только в `requirements.txt`
  каждого проекта с точным пиннингом `==`; в каждом `pyproject.toml`
  сохраняется `dependencies = []`. Dev-инструменты лежат один раз в корневом
  `requirements-dev.txt`.
- **Языковая политика (G-10).** Документы уровня репозитория — только на
  русском по замыслу; документы проектов — двуязычные пары (`README.md` ↔
  `README_ru.md`). Не добавляй суффикс `_ru` к репо-документам и не убирай
  его из проектных.

## Команды

Работай внутри папки проекта:

```bash
cd projects/NN-project-slug
pip install -e .
pip install -r requirements.txt
python -m pytest -v          # должно быть реально исполнено, никогда не «предположено»
ruff check .
black --check .
mypy --strict src            # strict только для 11-20; обычный mypy для 01-10
```

## Цикл разработки (на проект)

1. Lock scope (README фиксирует, чему учится; три этапа).
2. Пишем код minimal → improved → production-like.
3. Technical review: фактически запусти pytest/ruff/black/mypy; исправь находки.
4. Pedagogical review: необъяснённая магия — это баг; нейминг должен быть
   понятен новичку.
5. Fix loop: максимум две итерации. Всё нерешённое идёт в
   `docs/known-issues.md` с тегом `[project-NN]`, проект закрывается как
   `done-with-known-issues`.
6. Отметь done в `docs/PROGRESS_ru.md` с реальной pytest-summary строкой.

Правило эскалации (G-01): если нашёл противоречие с ARCHITECTURE.md,
затрагивающее текущий или следующий проект — стоп и спроси автора. Если
далёкий проект — запиши в known-issues и продолжай.

## Конвенции кода внутри проектов

- Публичные функции/методы (не начинаются с `_`) требуют type hints и минимум
  одного теста (G-13); `cli.py`/`main.py` освобождены от критерия покрытия,
  но всё ещё типизированы. Критерий проекта 10 заменён самотестированием на
  встроенном demo-наборе.
- Основная логика никогда не живёт в CLI-файлах; CLI-файлы не содержат
  бизнес-правил.
- Env-хелперы следуют одному паттерну: валидируй `var_name`, делай strip
  значений, возвращай документированные дефолты, бросай `ValueError` при
  неправильном использовании. Каждая env-переменная из кода присутствует в
  `.env.example`.
- Стиль ошибок: `ValueError` для пользовательских ошибок, доменные результаты
  как `None`/`False`, HTTP-коды мапятся на уровне роутов (422 валидация,
  404 отсутствие, 401 auth). DELETE возвращают 204 с явно пустым телом.
- Комментарии объясняют *почему*, а не *что*. Понятность новичку важнее
  хитрости.

## Конвенции документации

- Двуязычные пары должны зеркалить смысл друг друга; меняя одну, меняй вторую.
- Шаблон проектного README фиксирован: lock scope → установка (`pip install -e .`,
  затем `pip install -r requirements.txt`, две отдельные команды) →
  использование → детали → этапы → API → тестирование → заметка ZuroKing →
  заявление об изоляции.
- Security-смежные проекты (12, 17 и интеграционные паттерны в 16, 18–20)
  несут видимые предупреждения «educational only». При правках держи их
  заметными.

## Замечания об окружении

- Машины разработки — Windows (PowerShell 5.1) + локально Python 3.12–3.14,
  тогда как CI пинает 3.11 — код должен оставаться совместимым с 3.11;
  не используй синтаксис 3.12+.
- Не редактируй русскоязычный Markdown через PowerShell-пайплайны
  `Set-Content`/`Get-Content` — PowerShell 5.1 портит UTF-8 кириллицу.
  Используй инструменты редактирования, сохраняющие кодировку.
- Версии инструментов запинены в `requirements-dev.txt` (`ruff==0.15.20`,
  `black==26.5.1`, `mypy==2.1.0`, `pytest==9.1.0`); не поднимай их без нужды.
