## 1. Цель репозитория

`basicthon` — открытый учебный репозиторий из 20 изолированных Python-проектов для начинающих
разработчиков, выстроенных по возрастающей кривой сложности (Foundations → Structures & Patterns →
Data & Algorithms → Systems & Integration). Каждый проект — самостоятельная единица: можно
скачать одну папку и она будет работать без остального репозитория.

Вторичная цель: репозиторий содержит авторские заметки и структуру, узнаваемо связанные с
ZuroKing, но не в ущерб читаемости кода для новичков. Заметки в `docs/zuroking-notes/` пишутся только там, где есть нетривиальный инсайт, на русском языке (GRILL2-11), 150–300 слов, один файл на проект максимум (`NN-slug.md`, совпадает с именем папки проекта), линкуются из `projects/NN-slug/README.md`.

Языковая политика (осознанное решение, не баг): документы уровня репозитория идут двуязычными парами (`docs/LEARNING-PATH.md` ↔ `docs/LEARNING-PATH_ru.md`, `docs/METHODOLOGY.md` ↔ `docs/METHODOLOGY_ru.md`, `docs/PROGRESS.md` ↔ `docs/PROGRESS_ru.md`). Суффикс `_ru` применяется только к документации внутри `projects/*/` (`README_ru.md`, `ELI5_ru.md`, `ARCHITECTURE_ru.md`), потому что англоязычный README проекта расширяет аудиторию для портфолио, а внутренняя методология репозитория — рабочий документ автора.

## 2. Модель агента и границы автономности

Реализацию ведёт агент OpenCode на модели Muse Spark 1.2 по следующему циклу:

1. Написание `ARCHITECTURE.md` (этот документ, уровень репозитория).
2. Прогон через `grill-me` (2–3 итерации), вывод вопросов/несостыковок автору.
3. Основной цикл на каждый проект:
   a. Написание файлов проекта.
   b. `code-review` написанного/изменённого.
   c. Исправление найденного.
   d. Повтор b–c до критериев готовности (см. раздел 8).
   e. Отметка модуля завершённым в `docs/PROGRESS.md` (todo-list репозитория).
4. После завершения каждого проекта — генерация документации:
   `README.md`, `ELI5.md`, `ARCHITECTURE.md` (только для проектов, где предусмотрен —
   см. раздел 6), и их русские версии с суффиксом `_ru`
   (`README_ru.md`, `ELI5_ru.md`, `ARCHITECTURE_ru.md`).

**Правило эскалации при архитектурном противоречии (G-01):** Агент действует по этому документу как по source of truth. При обнаружении противоречия:
- если противоречие касается текущего или следующего по `docs/PROGRESS.md` проекта — стоп и эскалация автору, ждать ответа, конвейер не продолжать;
- если противоречие касается проекта, до которого очередь дойдёт нескоро — фиксировать в `docs/known-issues.md` с тегом `[project-NN]` и продолжать конвейер без остановки.

`docs/PROGRESS.md` — единственный todo-list репозитория (см. раздел 7). `docs/known-issues.md` — журнал отложенных противоречий/замечаний.

## 3. Структура репозитория верхнего уровня

```
basicthon/
├── README.md
├── LICENSE
├── CONTRIBUTING.md
├── .python-version          # GRILL2-12: фиксирует "3.11"
├── requirements-dev.txt     # GRILL2-03: ruff/black/mypy/pytest — dev-инструменты репозитория
├── .github/workflows/ci.yml # GRILL2-07: discover + strategy.matrix по projects/*/
├── docs/
│   ├── LEARNING-PATH.md
│   ├── METHODOLOGY.md
│   ├── PROGRESS.md          # G-16/GRILL2-09: todo-list, summary-строка "N passed in Xs" на проект
│   ├── known-issues.md      # G-01/G-04: журнал отложенных противоречий
│   └── zuroking-notes/      # GRILL2-11: NN-slug.md на русском, 150-300 слов, линкуется из projects/NN-slug/README.md
├── scripts/
│   └── new_project.py       # GRILL2-10: принимает --slug и --package явно; спека отложена (G-19)
└── projects/
    └── NN-project-slug/
```

Каждый `projects/NN-project-slug/` — изолированный модуль. Нумерация двузначная (`01`–`20`),
слаг в kebab-case, без сокращений, понятных только автору. Имя Python-пакета (`package_name`) задаётся отдельно параметром `--package` при вызове `scripts/new_project.py` (GRILL2-10) — никакой автоматической транслитерации/маппинга из слага нет.

**CI (GRILL2-03, GRILL2-07):** `.github/workflows/ci.yml` состоит из двух стадий: (1) job `discover` делает listing `projects/*/` и передаёт список как output следующему job через `matrix` (не хардкодить список из 20 папок в yml); (2) каждый job матрицы устанавливает `requirements-dev.txt` (с pip-кэшем через `actions/cache` по хэшу `requirements-dev.txt`) для `ruff`/`black`/`mypy`/`pytest`, затем ставит `requirements.txt` своей папки и запускает `ruff check`, `black --check`, `mypy` (см. GRILL2-04), `pytest -v` только внутри этой папки, используя конфиг из `pyproject.toml` этого же проекта. Будущий `ci.yml` должен явно фиксировать версию интерпретатора через `actions/setup-python` с `python-version: "3.11"` в каждом job матрицы, а не полагаться на системный Python раннера; локальные прогоны technical review могут идти на любой доступной 3.11+ версии — это не блокирует прогресс, но сам `ci.yml` при его написании обязан быть явным. Единый прогон в корне не используется.

## 4. Структура отдельного проекта

```
projects/NN-project-slug/
├── README.md
├── README_ru.md
├── ELI5.md
├── ELI5_ru.md
├── ARCHITECTURE.md        # только для проектов из раздела 6
├── ARCHITECTURE_ru.md     # только для проектов из раздела 6
├── pyproject.toml         # GRILL2-01: стандартный, без лишних инструментов вроде poetry; [build-system] (setuptools), [project] name/version="0.1.0"/requires-python=">=3.11", [tool.ruff], [tool.pytest.ini_options]
├── requirements.txt       # G-07: присутствует всегда; для stdlib-only — пустой с комментарием "# stdlib only, no external dependencies"; единственный source of truth для runtime-зависимостей (GRILL2-02)
├── .env.example           # GRILL2-06: обязателен для любого проекта с os.environ/секретом; минимум 12,13,14,16,17,18,19,20
├── src/
│   └── package_name/      # имя задаётся параметром --package (GRILL2-10), не выводится из слага
│       ├── __init__.py
│       └── ...
└── tests/
    └── test_*.py
```

Каждый проект — полностью изолирован: свой `pyproject.toml` (стандартный, без лишних инструментов вроде poetry — GRILL2-01) с секциями `[build-system]` (setuptools), `[project]` (`name`/`version="0.1.0"`/`requires-python=">=3.11"`), `[tool.ruff]`, `[tool.pytest.ini_options]`; `dependencies = []` всегда пустой (GRILL2-02). Runtime-зависимости — только в `requirements.txt` (единственный source of truth). Общего `pyproject.toml` на уровне репозитория нет (G-02). CI матрицы использует конфиг каждого проекта отдельно.

Установка для локального запуска/тестов (GRILL2-02): первым шагом в `README.md`/`README_ru.md` каждого проекта указываются две отдельные команды:
```
pip install -e .
pip install -r requirements.txt
```

`requirements.txt` присутствует всегда без исключений (G-07). Для stdlib-only проектов файл содержит единственную строку-комментарий: `# stdlib only, no external dependencies`. Для проектов с внешними зависимостями используется точный пиннинг `==` (G-17/GRILL2-12).

`.env.example` обязателен для любого проекта, где в коде используется `os.environ` или есть конфигурационный секрет/ключ/пароль (GRILL2-06); как минимум подпадающие: 12, 13, 14, 16, 17, 18, 19, 20.

## 5. Технологические стандарты

- Python 3.11 (фиксируется файлом `.python-version` со значением `3.11` в корне, GRILL2-12; все `pyproject.toml` используют `requires-python = ">=3.11"` без исключений и без per-project расхождений), обязательные type hints во всех публичных функциях/методах.
- `pytest` для тестов. Критерий покрытия (G-13, уточнён GRILL2-05): "основная логика" = весь код в `src/`, кроме файлов, целиком состоящих из CLI-парсинга и вывода (`cli.py`, `main.py`). Каждая публичная функция/метод (не начинается с `_`; методы классов считаются наравне с функциями верхнего уровня) вне CLI-файлов имеет минимум один тест. Исключение: №10 (мини-фреймворк тестирования) — критерий заменяется на "фреймворк корректно тестирует сам себя на встроенном demo-наборе". Процентный порог не используется.
- `ruff` для линтинга, `black` для форматирования, `mypy` для типизации — конфиг в `pyproject.toml` каждого проекта (секции `[tool.ruff]` и `[tool.pytest.ini_options]` для pytest; настройки black/mypy — также в `pyproject.toml` проекта). Сами инструменты `ruff`/`black`/`mypy`/`pytest` — dev-инструменты репозитория из корневого `requirements-dev.txt` (см. §4 про `dependencies`), а не зависимости отдельных проектов (GRILL2-03). Конфиг на уровне репозитория не используется (G-02, G-18).
- Зависимости — минимальные; stdlib предпочтительнее сторонних библиотек там, где это не противоречит цели проекта (например, №13–19 по определению требуют `requests`/`httpx`/FastAPI/aiogram/etc). Никаких общих runtime-зависимостей между проектами (см. раздел 3 — намеренная изоляция). `requirements.txt` — единственный source of truth (GRILL2-02), `pyproject.toml:dependencies = []`.
- Пиннинг версий (G-17, GRILL2-12): для проектов с внешними зависимостями `requirements.txt` использует точный пиннинг (`==`), не диапазоны; `requires-python = ">=3.11"` везде.
- Тесты без сети (G-12): все тесты в CI обязаны работать без сети и без реальных API-ключей. HTTP-запросы — через `unittest.mock`/`responses`, Telegram — через мок `update`-объектов, Ollama-клиент — тесты мокают HTTP-слой библиотеки, реальный инференс не тестируется в CI. `.env.example` — см. GRILL2-06.
- Языковая политика — см. раздел 1 (G-10): `_ru`-суффикс только для `projects/*/`, repo-level — только русский (осознанное решение).

## 7. Методология разработки (ссылка на docs/METHODOLOGY.md)

Для каждого проекта:

1. **Lock scope** — 2–3 предложения в README: что изучается, три этапа (minimal → improved → production-like).
2. **Написание кода** по этапам.
3. **Technical review** — фактический автоматический прогон `pytest -v` + `ruff check` + `black --check` + `mypy` (уровень строгости см. раздел 8, GRILL2-04) (не текстовое заявление агента, G-18), плюс ручная проверка багов/уязвимостей и соответствия разделу 5.
4. **Pedagogical review** — отдельный проход: понятен ли код новичку, нет ли необъяснённой "магии", логичны ли имена для обучающего контекста. Заметки `docs/zuroking-notes/` не являются обязательным критерием этого review (G-15); заметки на русском, `NN-slug.md`, линкуются одной строкой в конце `README.md` (GRILL2-11).
5. **Fix loop** — максимум 2 итерации после review, критерий выхода: 0 багов, 0 непояснённых мест, а не "до идеала".
6. **Done** — тесты реально зелёные (`pytest -v`, вывод не выдумывается), документация сгенерирована (раздел 8).

**Правило исчерпания fix loop (G-04):** Если после 2 итераций fix loop остаются непокрытые замечания — они переносятся в `docs/known-issues.md` с тегом `[project-NN]`, модуль всё равно закрывается как Done, но помечается в `docs/PROGRESS.md` статусом `done-with-known-issues` вместо `done`.

**Todo-list и артефакты (G-16, GRILL2-09):** `docs/PROGRESS.md` — единственный todo-list репозитория, простой markdown-чеклист по всем 20 проектам. Полный вывод `pytest -v` живёт только в CI-логах (не коммитится). В `docs/PROGRESS.md` на проект хранится только summary-строка (например, `23 passed in 1.2s`), не полный вывод.

## 8. Критерии готовности модуля ("Definition of Done")

Модуль считается завершённым, когда:

- [ ] Код проходит technical review без открытых замечаний (фактические прогоны, G-18).
- [ ] Код проходит pedagogical review без открытых замечаний.
- [ ] `pytest -v` — все тесты зелёные; полный вывод — в CI-логах, в `docs/PROGRESS.md` — только summary-строка (GRILL2-09).
- [ ] `ruff check` — без ошибок.
- [ ] `black --check` — без изменений (G-09).
- [ ] `mypy` — без ошибок, уровень строгости по группе проекта (GRILL2-04):
  - проекты 01–10 (Foundations, Structures & Patterns): обычный `mypy` (без `--strict`);
  - проекты 11–20 (Data & Algorithms, Systems & Integration): `mypy --strict`.
- [ ] README.md / README_ru.md — присутствуют, описывают 3 этапа и заметку от ZuroKing; первыми шагами установки указаны две команды `pip install -e .` и `pip install -r requirements.txt` (GRILL2-02); для проектов с `docs/zuroking-notes/NN-slug.md` — в конце `README.md` присутствует строка `См. также: заметка автора` со ссылкой на `docs/zuroking-notes/NN-slug.md` (GRILL2-11).
- [ ] ELI5.md / ELI5_ru.md — присутствуют.
- [ ] ARCHITECTURE.md / ARCHITECTURE_ru.md — присутствуют, если проект отмечен в разделе 6 (критерий G-03).
- [ ] `requirements.txt` — присутствует (G-07, GRILL2-02 — единственный source of truth, `pyproject.toml:dependencies = []`); для проектов с внешними зависимостями — с точным пиннингом `==` (G-17, GRILL2-12); `requires-python = ">=3.11"` в `pyproject.toml` (GRILL2-12); `.env.example` — присутствует для любого проекта с `os.environ`/секретом, как минимум 12,13,14,16,17,18,19,20 (GRILL2-06).
- [ ] Модуль отмечен в `docs/PROGRESS.md` статусом `done` или `done-with-known-issues` (G-04, G-16) с summary-строкой pytest (GRILL2-09).

## 9. Явные не-цели (Out of Scope)

Зафиксировано, чтобы агент не расширял объём самостоятельно:

- Не строим общий CLI-раннер, объединяющий все 20 проектов в одну команду.
- Не делаем shared/-модуль с переиспользуемым кодом между проектами (см. раздел 3).
- №12 (менеджер секретов) — учебная реализация с явной пометкой "не для реального использования"; не следует уровню строгости `secure-secrets-vault` (портфолио-проект #8, отдельный репозиторий).
- Не добавляем Docker/деплой-инфраструктуру — вне цели чисто учебного репозитория.
- **Ровно 20 проектов (G-05).** Добавление 21-го и более требует явного письменного решения автора вне цикла `grill-me`/`code-review`. Агент не предлагает и не создаёт дополнительные проекты самостоятельно.
- **Исключение для №20 (G-08, уточнено GRILL2-08):** проекту №20 явно разрешено копировать и адаптировать код из №04, №11, №16 (copy-paste, НЕ `import` между папками проектов) для сохранения изоляции. Это снепшот на момент создания №20, без обязательства синхронизации с исходниками при их последующих изменениях — trade-off изоляции vs дублирования. В `README.md`/`README_ru.md` проекта №20 обязательны две пометки: (1) "Этот проект переиспользует паттерны из проектов 04, 11, 16 — код скопирован и адаптирован, не импортирован, для сохранения изоляции проектов"; (2) "Снепшот на момент создания — последующие изменения в 04/11/16 не портируются автоматически". Это единственное исключение из запрета `shared/`.
